\begin{lemma}[Kernel acceptance boundary machine export sibling route]
\label{lem:kernel-acceptance-boundary-machine-export-sibling-route}
Every $\MachineExportBoundaryUp$ consumer of \autoref{ch:concrete-instances-machine-export-boundary-namecert} may consume $\KernelAcceptanceBoundaryUp$ only after the accepted-declaration row and the axiom-query refusal row have both been displayed. Concretely, the consumer first reads the accepted-declaration exposure route of \autoref{thm:kernel-acceptance-boundary-accepted-declaration-exposure}, then the acceptance-audit dependency route of \autoref{thm:kernel-acceptance-boundary-acceptance-audit-dependency-route}, and only then the machine-export forward route of \autoref{thm:kernel-acceptance-boundary-machine-export-forward-route}. The sibling route therefore exports a boundary for machine-facing declaration handoff, not kernel self-correctness, compiler correctness, hardware trust, semantic adequacy of theorem names, or a detached machine target.
\end{lemma}
\begin{proof}
Project the $\KernelAcceptanceBoundaryUp$ carrier
$$
Q=(G,K,A,E,L,F,H,C,P,N).
$$
The row $A$ is the accepted-declaration coordinate and the row $F$ is the axiom-query refusal coordinate.

Apply the accepted-declaration exposure theorem. It places $A$ downstream of the generated candidate, classifier stamp, environment ledger, replay ledger, refusal row, transport, continuation, provenance, and local naming.

Apply the acceptance-audit dependency route. It requires the accepted-declaration source route and the forbidden-ancestry refusal route to be visible together before the local boundary can be consumed.

Finally read the machine-export forward route. Since that route consumes the same $A$ and $F$ rows before exposing a machine-facing export, the sibling link to \autoref{ch:concrete-instances-machine-export-boundary-namecert} cannot bypass either displayed dependency row or import any of the excluded correctness claims.
\end{proof}
